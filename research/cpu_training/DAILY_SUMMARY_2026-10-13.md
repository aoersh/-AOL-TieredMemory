# CPU DNN + CXL 阶段总结（2026-10-13）

## 完成范围

按10-12讨论补充原生参考，并将快内存配额从额外saved副本扩大到全部经C10 CPU
allocator分配的张量存储。正式完成36个独立计时进程、10个诊断进程，矩阵随机串行，
每计时进程5预热+100正式。没有重跑10-12矩阵，没有改内核/sysctl或做新perf采样。

环境仍为6.8.12-138-soaralto、真实CXL node2/DRAM node0、训练CPU0–7，
FP32 eager Transformer batch8/sequence512/width128/heads4/layers2、SGD。
固定输入仅用于系统性能与数值对照，不声称真实数据训练收敛。

## 原生框架校准

native/受管全部副本DRAM/受管Direct CXL三个条件各五独立进程，数值状态hash一致。
native不做保存副本，保留旧runner公共记账；其他两组fresh复制134.15625 MiB/步。

| 路径 | 整步 ms | 相对native差 ms [95% CI] |
|---|---:|---|
| native | 72.033 | 参考 |
| 受管DRAM | 111.863 | +39.830 [28.007,51.653] |
| 受管Direct CXL | 88.291 | +16.259 [6.862,25.655] |

完整run也保持相同判断。旧副本框架有显著额外成本；Direct相对受管DRAM较快不代表
CXL硬件较快。差值包含整个分配、保存和计算环境变化，不能全部归于memcpy。
这也不是整进程DRAM与整进程CXL的比较。

## 无保存副本的张量配额筛查

新增进程内C10 CPU allocator，首次分配直接在节点0/2创建storage，无保存副本复制、
无迁移，预约按4 KiB页对齐，munmap完成后退款。所有受管条件共用该实现。
诊断确认参数/输入、每步56次保存storage、梯度和所有活跃分配记录，原生三步
loss/梯度/参数状态hash一致，结束时全部预约和映射释放，零分配失败。

| 路径 | 整步 ms | DRAM张量预约峰值 MiB |
|---|---:|---:|
| 默认原生 | 67.289 | 未由新分配器计数 |
| 新allocator全部DRAM | 119.379 | 178.402 |
| 新allocator全部CXL | 102.937 | 0 |
| 分配顺序first64 | 98.687 | 63.895 |
| 分配顺序first128 | 105.397 | 127.855 |
| ≤1 MiB优先small64 | 104.527 | 3.324 |
| ≤1 MiB优先small128 | 104.977 | 3.324 |

七条件各三独立进程，配对t(df=2)，未校正多重比较。
first64−CXL为−4.251 ms [−11.450,2.949]，点估计约快4.13%，但区间跨零。
small64−first64为+5.840 ms [−5.386,17.067]，small128−first128为
−0.421 ms [−7.901,7.060]，均无稳定同预算规则赢家。
small只用3.324 MiB，两档上限未改变准入，不能据此评价预算增加的作用。

新allocator全DRAM−默认原生为+52.089 ms [40.408,63.771]；缺页约149481 vs
68404次/步，逐次mmap/mbind/munmap仍造成明显分配压力。没有新的采样或因果
干预，不能把耗时全归为缺页/LRU，也不能把全CXL较快当硬件访问优势。
本批不与上面的五进程框架校准或历史批次拼接绝对时间。

## 边界与决定

容量账本已经覆盖参数、梯度、临时存储等C10张量分配，范围比旧副本池更完整，
但解释器、库内部直接malloc和安装前分配仍不受限，**不是真正整进程DRAM限额**。
诊断first64第二步backward前，node0无file字段匿名映射约380.637 MiB，
张量node0预约只有63.805 MiB；参考训练的默认allocator缓存也在诊断残余中。
节点记录是诊断时点，不是正式连续峰值或完整后台工作区分解。

本轮有限筛查没有通过稳定实用收益门槛，停止扩大当前shape、配额或大小阈值，
不进入动态迁移、AOL或复杂ML；区间较宽也不能证明所有分配规则都无用。
后续若继续，先解决分配器开销和可核验的容量边界，例如固定节点有界池复用及
账本外内存分解，再决定是否值得测试策略。池化和整进程容量控制尚未实施。
普通cgroup memory.max限制总内存，现有SOAR拦截器只预算部分大malloc，不能
直接把任一工具当成PyTorch整进程DRAM上限。
